# CPU Observation Experiment

## Overview

- Run ID: `cpu_observation_20260426_113820`
- Goal
  - Compare `-x 0` (`GPUD`) and `-x 2` (`CPU_GPU`) under a small set of representative workloads.
  - Check whether GDS direct path reduces CPU cost when throughput is similar.
- Raw benchmark summary
  - [`docs/data/cpu_observation_20260426_113820_summary.csv`](/home/poc/gds_bench/docs/data/cpu_observation_20260426_113820_summary.csv)

## Method

- Tool
  - `gdsio`
- Runtime
  - `10s`
- Repeats
  - `3`
- GPU
  - `GPU 0`
- Dataset preparation
  - Enabled
  - `PREP_X_FLAG=2`
  - `PREP_IO_SIZE=1M`
- CPU samplers
  - `pidstat`
    - Used for `gdsio` process `%CPU`, `%usr`, `%system`
  - `mpstat`
    - Used for system `%usr`, `%sys`, `%iowait`

## Path Validation

- `gdsio.log` was used as the primary per-case path evidence.
  - `-x 0` cases reported `XferType: GPUD`
  - `-x 2` cases reported `XferType: CPU_GPU`
- cuFile debug logs were used as secondary evidence.
  - Observed messages such as `gds path taken with ODIRECT`
  - Observed `nvfs_io_submit`
  - Observed `nvfs > 0` and `posix = 0` in the cuFile summary
- Conclusion
  - The tested `-x 0` cases did run through the intended GDS/nvfs path.
  - The observed CPU behavior was not explained by fallback to POSIX mode.

## Key Observations

- Sequential read did not show the expected CPU-offload benefit for `-x 0`.
  - Throughput was nearly identical between `-x 0` and `-x 2`.
  - However, `gdsio %CPU` was consistently higher for `-x 0`.
  - The extra CPU cost of `-x 0` was concentrated in `%system`, not `%usr`.
- Sequential write showed the same direction.
  - `-x 2` was slightly faster on average.
  - `-x 2` also used less `gdsio` CPU than `-x 0`.
- Random write behaved differently.
  - `-x 2` delivered much higher throughput and IOPS.
  - `-x 2` also used more CPU, which is consistent with doing substantially more work.
- The most important pattern in this run was not a throughput gap.
  - It was the shift in CPU cost composition.
  - `-x 0` tended to spend more CPU in `%system`.
  - `-x 2` tended to spend more CPU in `%usr`.

## Conclusion

- On this platform and under these four workloads, the experiment did not show a clear CPU-efficiency advantage for `-x 0`.
- For the sequential read workloads, `-x 0` and `-x 2` achieved similar throughput, but `-x 0` consumed more `gdsio` CPU.
- The result suggests that, in this environment, the cost removed from the CPU-bounce copy path was not enough to offset the control and kernel-side overhead of the GDS path.
- Therefore, this CPU-observation run does not support the claim that GDS reduced CPU utilization on this system for the tested workloads.
